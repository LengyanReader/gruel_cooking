## 一、总体判断

本仓已从「九支柱理念仓」演化为「**三线工作坊 + 工具带**」：**文化月旦（culture_review）、数学澄清（math_clarification）、科研侦察（academic_research→reseArch_X）** 三线高度活跃且纪律渐佳，配套生成器/门禁/音频管线自成体系；而 README 承诺的九支柱中 **5 个仍是骨架或休眠**（core、heaven_climate、economics_cross_culture、contemplative science、direction_refs）。最大的结构性风险不是内容不足，而是：**门禁与 CI 的倒挂**（休眠模块有 CI、活跃模块靠本地自觉）、**docs/ 的 61MB 音频随月刊重生成而膨胀**、以及**三层 harness 概念与 README 理想架构之间的导航成本**。

## 二、分维度评估

### 1. 内容维度
- **强**：三旗舰的内容纪律已成体系——culture_review 有订正登记+凡例+逐条回源（⑬条订正可查）；math_clarification 有 citation_audit（75 引文双侧）+ venue memo 决策记录 + 撤稿装置的字节级存档；reseArch_X 有 scan_log 四轮台账、✔/◐/◇ 三级标注、先验纠错留痕（本会话 3 处）。
- **弱**：README 的「Five/九 Pillars」叙事与现实严重脱节——core/heaven_climate/economics 只有 Working Method 骨架；contemplative science、direction_refs 连 README 都是空的；**新访客按 README 导航会三次落空**。
- **内容单点**：Reading_IA 承诺「个人知识管理系统」，实际 readings/library 仅书卡 5 张——深度在 web/corpus JSON（23MB），广度在册页，中间层薄。

### 2. 结构维度
- **IA 漂移**：根目录实际 13+ 个内容目录 vs README 的 9 支柱；`academic_research`（方向侦察）与 `reseArch_X`（机会层）已声明层级关系但物理分离、README 各说各话。
- **三重 harness 概念**：`harness/`（仓手册）· `.harness/`（reseArch_X 任务 harness）· 外部 `<HF>` harness_factory（常驻引用）——三者在名字上不可分辨，新会话/新读者需要一份导航说明（谁管什么、入口各在哪）。
- **双轨发布**：各模块 web 生成物集中在 `docs/`（落地页 index.html 手工维护 20+ 目录组），与各模块 README 又一层重复——三处（README、index.html、模块页）任何一处改结构都要三处同步，已现漂移征兆。
- **根目录卫生**：`_nr.txt`(226KB)、`_qid_verify.txt`、4 个临时脚本、`test` 文件散落根目录；`math_clarification/docs/vc.md`（一行会话 ID）等未跟踪残件分布在模块内。

### 3. 功能维度
- **生成器/门禁清单**（这是本仓真正的「功能」层，共 7 套）：
  1. culture_review：build_audio + verify_audio（ALL OK）+ pron_audit；
  2. math_clarification/essays：build_reader（--check）+ refcheck + review_scope；
  3. reseArch_X：build_reseArch_X（26 学者仪表盘，106KB）；
  4. discovery_atlas：gate.py（schema 校验）+ build_view/build_graph + resolve_qid；
  5. math_clarification/web：L0–L5 分级 viewer；
  6. Reading_IA：fabric 门禁（有 CI）+ web corpus；
  7. living_heritage：pytest + Docker + CI。
- **CI 倒挂**（核心发现）：有 CI 的三个（living_heritage、Language Stacking、Reading_IA）恰是低频/停滞线；**最活跃的四个模块（culture_review、math essays、reseArch_X、discovery_atlas）的门禁全部只在本地跑**——一旦换机器/换会话/多人协作，门禁即失效。M3「硬门必须机械强制」原则在仓级未闭环。
- **Windows 本地工具链**：cp1252 控制台对 utf-8 符号（✔/○）不友好（本会话两次踩坑）；CRLF 警告每次提交刷屏——缺 `.gitattributes` 统一策略。

### 4. 工程维度
- **音频即资产也即负担**：44 个 ogg/61MB 入库，月刊全量重生成意味着每次校订都新增 ~50MB 级 blob 到历史（pack 已 101.5MiB）；`_audio_cache` 等缓存正确未入库，但历史里的旧音频只增不减。
- **大 JSON 入库**：Reading_IA/web/data/corpus 8 卷 JSON（数百 KB 级）随内容演进会制造 diff 噪音与历史膨胀。
- **无 `.gitattributes`**：CRLF/LF 混乱（每次提交 10+ 行警告）；`* text=auto eol=lf` 一行可治。
- **无统一 entrypoint**：7 套生成器各在各自目录，无 `make`/`task` 层；新会话要知道「先跑哪个再跑哪个」只能读台账。

### 5. 治理与协作
- **强**：reseArch_X 的任务 harness（PLAN/PROGRESS/scan_log/能力台账）是全仓治理示范；「先验证再称完成」在三旗舰已内化为门禁；多会话并行（本会话与他会话同日各自提交 5d56745/2115582）靠 git 天然协调，暂无冲突。
- **弱**：① `tasks/` 只服务 reseArch_X 一线，culture_review/math 线无对应 PLAN/PROGRESS（会话协议按 AGENTS.md 只覆盖本 harness 目录）；② harness/README 的 W-CAP 等流程与实际执行（scan_log 台账）有重合但未互链；③ 全仓「溯源债」无统一台账——各模块 ◇/◐ 分散在档案里，无一张总清单与清偿排程。

### 6. 发布与可见性
- GitHub Pages 落地页 + 各模块离线站（culture_review 音频交互、星座图、L0–L5 数学阅读器）是**差异化亮点**——但 Pages 站点的构建全靠本地手跑后 push，无 Pages Actions 自动化；落地页与 README 的模块清单已经不一致（落地页 20+ 组 vs README 9 支柱）。

## 三、优化建议（按优先级）

### P0 · 本周（低成本高杠杆，全部可机械验证）
1. **CI 补齐四个活跃模块**：为 math essays（build_reader --check + refcheck + review_scope）、reseArch_X（build_reseArch_X + 可加 --check 模式）、discovery_atlas（gate.py）、culture_review（verify_audio）各加一个 path-filtered workflow——把已有门禁升为硬门（M3），每项 ~20 行 yaml。
2. **`.gitattributes` + 编码卫生**：`* text=auto eol=lf`、`*.ogg binary`；Python 脚本统一 `sys.stdout.reconfigure(encoding='utf-8')` 惯例。
3. **根目录清扫**：散件移入 `scripts/scratch/`（或经你确认后删除）；`math_clarification/docs/vc.md` 处置；`.gitignore` 增补 `_audio_cache/`、`_ex/`、`_fig1_check.png`、`.kilo/` 等已见残件。
4. **README 对齐现实**：改为「三条活跃线 + 工具带 + 骨架区（明确标 status）」的诚实分层；落地页 index.html 与 README 共用一张模块清单数据（进 README 的 yaml 头或独立 manifest，二者从同一源渲染）。

### P1 · 本月
5. **音频策略决断**（需要你拍板，三选一）：a) ogg 出库改 Git LFS；b) 音频改 Pages 构建时生成（repo 只留 build_audio.py + 文本源）；c) 维持现状但每期保留前清理历史（filter-repo）。推荐 b 或 a——61MB/月的历史增速不可持续。
6. **「溯源债」总台账**：把全仓 ◇/◐（QID 回填、一手直链、指导谱系、msca watchlist 等）汇成一张带排期的表（建议 `harness/DEBTS.md` 或 scan_log 总册），按对话优先级清偿——把分散在各档案的「待补」变成可管理的队列。
7. **统一 entrypoint**：`tasks/make.md` 或简单 `Makefile`/`justfile`：`check-all` 串起 7 套门禁；新会话开场一条命令自证仓库健康。
8. **harness 三层导航说明**：在 `harness/README.md` 顶部加一节「harness 一词在本仓的三个含义」（仓手册 / 任务 .harness / 外部工厂），各给入口。

### P2 · 本季
9. **骨架区决断（component-ablation）**：core/heaven_climate/economics_cross_culture 三选一策略——喂料（economics 已是 Hui/Ray 两位新学者的 MVP 语料，最接近激活）、合并（contemplative science 并入 reseArch_X 修行轴）、或冻结（明确标 archived，README 撤 promise）。
10. **living_heritage 复活决策**：全栈 app+CI 齐备但停滞月余——它是「走廊深图」（Kenderdine 对话）与「碳足迹审计」（Gössling）的现成载体，建议绑定 reseArch_X 的 MVP-002 排期，否则显式降级。
11. **Pages 自动化**：GitHub Actions 构建各生成器后部署 Pages（与 P0-1 同一工作流家族），落地页渲染自动化。
12. **Reading_IA 中间层**：书卡 5 张与 23MB corpus 之间补「月度 brief → 主题档案」的常规节奏（moment/ 已有骨架），或显式收缩承诺。

## 六、勘误（2026-11-04，发布后复核 · 只追加）

1. **Reading_IA「大 JSON 入库」不实**：`Reading_IA/web/data/corpus/`（8 卷 pe-*.json）本就被 `.gitignore` 排除（「阅读语料中间产物…禁止入库」），实际入库仅 books.json 684KB / authors.json 96KB 等，体量健康。原工程维度第 2 条与记分卡中相关表述作废；`.gitignore` 的既有策略应记为**正面样本**。
2. **direction_refs「空壳」不准**：`direction_refs/*` 系 `.gitignore` 有意排除的本地区（有意仅本地），非失管空壳。
3. **音频清单口径**：入库 ogg 为 44 轨/61MB（评估时曾按 docs 盘占 225MB 口径混算——其含本地缓存），结论不变：历史增量随月刊重生成累积。
